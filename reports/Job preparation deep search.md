# Bounded pipeline keeps deep search under NZ$0.10 a run

The deep-search agent should be a fixed LangGraph pipeline with one bounded retry, not a free tool-calling loop, and it should run only on jobs the user flags. Each run makes up to four search queries, six page reads and about a dozen small model calls, which comes to roughly **US$0.04 (about NZ$0.07) per run** at current Anthropic prices, so **50 to 60 deep runs a month cost about NZ$4**, leaving room in the NZ$5-10 budget. The pack should cover eight sections, led by a job-to-evidence map and interview-stage prep, with every employer fact tied to a source URL and every pay figure labelled with its source, date and method. Sources are limited to Google Places (for location and basic business facts), the employer's own website, the public NZ company registers once a subscription is confirmed, Tavily search (already in use) and Jina Reader, plus the user's resume, the pasted job description and any user-supplied link that is not on a blocked domain. SEEK, LinkedIn, Indeed and Glassdoor are never fetched, and the blocklist is enforced in code before any URL is requested. Several inputs are still unverified (Places field-to-SKU mapping, Places caching terms, Tavily credit cost, and the Companies Office API schema), so they must be checked before the first build.

## What the pack should contain, in priority order

Recruiter and careers guidance in NZ converges on the same core. The [Tahatū interview tips](https://tahatu.govt.nz/work/doing-an-interview/tips-for-interviews) say to research the organisation's culture and what it wants in an employee, to re-read the job description, to prepare examples that show how skills were used, and to draft questions from the research. The [Trade Me interview guide](https://www.trademe.co.nz/c/jobs/article/how-to-prepare-for-a-job-interview-nz) adds that salary should not be raised in a first interview unless the interviewer raises it, and that logistics (route, parking, arrival 10 to 15 minutes early, video tech) need planning. The notes do not show any NZ-specific guide on culture, referees or work rights, so the pack should flag those as unknown rather than fill them with general advice.

Based on those sources, the pack should have eight sections. The first is a **job-to-evidence map**: each must-have and nice-to-have from the advertisement, paired with a STAR example from the user's resume, and each gap marked for the user to address. The second is **interview stages and format**, listing the likely stages (recruiter screen, possibly an AI-led first call, a technical screen or take-home, pair programming, a values conversation, a final panel) with the format marked as unconfirmed until the recruiter says so. The third is a **pay band**, built from the posted range if one exists, then from two or more sources that each carry a date and method. Hays figures are base salary only and exclude KiwiSaver, Payscale and Indeed figures are self-reported or job-ad based, and no verified Wellington or Hamilton developer median was found. The fourth is **employer and team research**, limited to public facts with links (recent news, products, funding, restructures). The fifth is **questions to ask**, drafted from that research. The sixth is **technical prep**, the stack in the advertisement and a practice list. The seventh is **logistics**, covering commute at the interview hour, on-site versus hybrid versus remote status, and relocation. The eighth is **application tailoring**, meaning resume and cover-letter edits, where every claim must be checked against the user's own history because the hallucination risk is highest here.

The ranking is the notes' inference, not a sourced finding. No source measured which section most improves interview rates, so the report should present it as a design judgement. The notes also found that existing AI interview tools (Final Round AI, Teal, Huntr) mostly offer mock interviews, question banks and trackers, and that complaints centre on cost and on live in-interview copilots. The pack should therefore skip live assistance and focus on preparation content.

## Data sources and their hard limits

The notes favour a small allow-list because the budget rules out general web search at volume. Google Places (New) is the most useful source for location and basic business facts. Its billing rule bills a whole request at the highest SKU any requested field needs, so a Pro-tier field mask is the cheapest viable option. The notes cite a Google pricing page with free monthly caps of 5,000 Text Search Pro calls and 5,000 Place Details Pro calls per month ([Places usage and billing](https://developers.google.com/maps/documentation/places/web-service/usage-and-billing); [Google Maps Platform pricing](https://developers.google.com/maps/billing-and-pricing/pricing.md.txt)), but that page carried no date, and the field-to-SKU mapping and the storage and display terms were never retrieved. At one Text Search and one Details call per deep run, Places stays inside the free caps, though the agent should still keep a counter.

Tavily is the best choice for general search because it is already in the project. Its free plan gives **1,000 credits a month** and pay-as-you-go is **$0.008 per credit** ([Tavily pricing](https://tavily.com/pricing)), but the page does not say how many credits a basic search costs, so one credit per query is an assumption to test. At four queries per run, the free tier covers about 250 runs a month if that assumption holds. Brave ($5 monthly credit) and Exa ($10 starter credit) are fallbacks; the Brave page also contradicts itself on whether the free allowance is $5 or $20 ([Brave Search API](https://brave.com/search/api/)).

Jina Reader fetches the employer's own pages as text. Basic use needs no key, and a free key includes **10M tokens** ([Jina Reader](https://jina.ai/reader/)). Its rate limits are stated inconsistently on the same page (20 RPM without a key, and 100 or 500 RPM with one), so the agent should throttle conservatively. Reader's per-million-token price was not retrieved.

The Companies Office and NZBN registers are the right source for legal name, entity status and registered office, but the notes could not read their API schema, rate limits or terms. They are available on the [MBIE API portal](https://portal.api.business.govt.nz/explore-apis) by subscription. Until the schema is read, the agent should use the employer website and Places for legal name and status, and should not promise register data in the pack.

The agent should not use Claude's server-side web search for this job. At $10 per 1,000 searches, it costs about **NZ$15 for 900 searches**, which exceeds the whole budget ([Claude web search tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)).

The blocked list is SEEK, LinkedIn, Indeed and Glassdoor, applied to search results and to any link the user pastes. LinkedIn's [User Agreement](https://www.linkedin.com/legal/user-agreement) explicitly prohibits automated access and collection "through third parties (such as search tools or data aggregators or brokers)", so a search API must not be used to pull LinkedIn profile data either. The SEEK, Indeed and Glassdoor terms were not retrieved, so the rule for those rests on the builder's policy. When a user gives a SEEK or LinkedIn link, the agent should ask the user to paste the relevant text instead of fetching it.

Personal data needs a narrow rule. Under the Privacy Act 2020, [IPP 2](https://www.privacy.org.nz/privacy-act-2020/privacy-principles/2/) allows collection from a public source where the information is "publicly available", but the OPC notes that public availability is not automatic. The conservative rule for the tool is to collect only a hiring manager's business role and employer-published contact details, record the source and date, and delete them when the application closes. The tool should not build personal profiles.

## Architecture: a fixed graph with one bounded retry

The notes recommend a hand-written LangGraph `StateGraph` rather than the prebuilt agent, because a fixed topology is cheaper, easier to test, and easier to audit. The LangGraph v1 release notes say `create_react_agent` is deprecated in favour of `create_agent` ([LangGraph v1 release notes](https://docs.langchain.com/oss/python/releases/langgraph-v1)), so new code should not start from it. The graph runs `plan` (Haiku 5.5, no tools, up to four queries and the required fields), then `search` (Tavily, merged, deduplicated and filtered against the blocklist), then `read` (Jina Reader, up to six URLs, each truncated to about 6K tokens and stored as untrusted text with an ID), then `extract` (Haiku 5.5, one call per page, returning facts with a source ID and a verbatim quote of up to 25 words), then `gap_check` (plain code, which loops back to `search` once if required fields are still empty and budget remains), and finally `write` (Sonnet 5.5, structured output through `messages.parse()`, with quote validation and one retry).

Safety rests on the code rather than the prompt. Anthropic's [prompt-injection research](https://www.anthropic.com/research/prompt-injection-defenses) reports a best case of 1.4% attack success for Opus 4.5 with improved safeguards and calls that "meaningful risk", so the agent should treat every fetched page as hostile. It should give the agent no tools that act on the web, reject any fact whose source ID does not exist or whose quote is not found in the stored text (after whitespace normalisation), and mark anything unquotable as "could not verify". Every budget should be a counter in state, checked before each node, because `recursion_limit` is only a backstop. The notes also disagree on the default limit (a documented 9,999 for `create_agent` versus 25 for graphs in secondary sources), so the builder should set it explicitly.

Two model settings matter for cost. Thinking is adaptive by default on Haiku 5.5, and the skill's reference states that Haiku 5.5's default effort is `medium`, so extraction calls should set `output_config` effort to `low` explicitly and cap `max_tokens`, because thinking tokens bill as output. Forced `tool_choice` returns a 400 on Sonnet 5.5 and Haiku 5.5, so the plan and extract steps should use structured output rather than a forced tool call. The project's own API key must be read from the project environment, never from the shell's ambient Anthropic key.

## Cost controls and the monthly budget

The per-run arithmetic in the notes checks out against the current prices. Anthropic's pricing lists Haiku 5.5 at $0.10 input and $0.50 output per million tokens, Sonnet 5.5 at $2 and $10, and Opus 5.5 at $4 and $20 ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)); the price table cached in the claude-api skill (dated 3 November 2026) gives the same figures. Using those, the fixed pipeline costs about **$0.004 on Haiku plus $0.039 on Sonnet, or about US$0.043 per run**. An agent loop on Haiku with Anthropic's server search costs about US$0.19 per run, and the same loop on Sonnet about US$0.50, so both are poor fits. Correcting one figure in the notes, using Opus 5.5 for the synthesis step instead of Sonnet raises the run to about **US$0.08**, not US$0.07.

| Design | Approximate cost per run | Verdict |
|---|---|---|
| Fixed pipeline, Tavily and Jina outside Anthropic, Sonnet 5.5 synthesis | US$0.043 (about NZ$0.07) | Recommended |
| Same pipeline, Opus 5.5 synthesis | US$0.08 (about NZ$0.13) | Only if measured quality requires it |
| Haiku loop with Anthropic server search | US$0.19 | Over budget at scale |
| Sonnet loop with Anthropic server search | US$0.50 | Not viable |

At an assumed rate of about US$0.60 per NZ dollar (not checked), NZ$10 buys about 140 runs of the recommended design and NZ$5 about 70. The sensible monthly cap is therefore **60 deep runs**, costing about NZ$4.30 in model calls before search and reader quotas. Those runs should be limited to shortlisted jobs by an explicit per-job flag, not run on the full 30-a-day feed. Caching helps only modestly because each run uses a different job; the cache that matters is per employer, so a second role at the same company reuses the first run's employer facts.

The code should enforce four layers of control. A per-run budget of 4 queries, 6 page reads, 12 model calls and a dollar estimate, checked before each call, stops a run that hits any limit and records which rule fired. A monthly counter in the database blocks new deep runs once the 60-run cap is reached and reports the count in the UI. A Places counter keeps calls under the free caps. Finally, employer facts are cached by company, so repeat roles cost nothing extra. Measured token counts from ten real jobs should replace the estimates before the cap is set, because the 4K-per-page figure is an assumption.

## Gaps that block a confident build

Several inputs are not verified, and the report should not be read as settling them. The Google Places field-to-SKU mapping is unknown, so the builder cannot yet say whether reviews or ratings fall in a free tier, and Places storage and attribution terms were not retrieved, which decides how long place data can be cached. The Companies Office and NZBN API schema and terms are unread. Tavily's credit cost per basic search and per extract is unconfirmed. The Jina token price and per-page token counts are unmeasured. The exchange rate is assumed. The SEEK, Indeed and Glassdoor terms were not retrieved. No NZ source covers te reo, tikanga, work rights or referee norms, and the pack should label those as unknown. There is also no evidence on how often generated company facts are wrong, so the pack should mark every AI-written employer claim as unverified until the user checks the source.

## Conclusion

The useful change here is not a cleverer agent but a smaller, more honest one. A deep-search run is worth about NZ$0.07 when it is a fixed pipeline with hard caps, which means the budget is spent on deciding which jobs deserve a run, not on the model itself. The main risks are not cost but correctness and terms: a fact the model invents, a page that carries a hostile instruction, or a fetch of a blocked site. Those are controlled by quote validation, untrusted-text handling and a blocklist checked in code, rather than by prompt wording.

The pack's value depends on sections the sources cannot settle, especially the evidence map and the pay position, so the agent's job is to gather and cite facts while the candidate judges them. Before the first build, the builder should confirm the Places field mapping and storage terms, read the Companies Office API, measure Tavily's credit use on five real queries, and run ten jobs to replace the estimates in this report with measured figures.
